# C0.7 — Data reproduction and audit plan

Market data is deliberately not committed. This document plus
`research/datasets/dataset_v1.lock.json` is the whole contract for reproducing
it.

## 1. Exact specification of Dataset V1 (frozen)

| Field | Value |
| --- | --- |
| Exchange | Binance |
| Market type | **spot** |
| Pairs | `BTC/USDT`, `ETH/USDT` |
| Timeframes | `5m`, `1h` |
| Download timerange | `20250701-20260907` |
| Storage format | feather (Freqtrade `--data-format-ohlcv feather`) |
| 1h coverage | 2025-07-01T00:00Z → 2026-09-06T17:00Z, 10 386 rows |
| 5m coverage | 2025-07-01T00:00Z → 2026-09-06T18:50Z, 124 643 rows |

Fingerprints are in the lock file and match
`freqtrade/user_data/baseline_v1_data_audit.json`; a test asserts the two never
disagree.

## 2. Acquisition

```bash
cp freqtrade/user_data/config.paper.json.example freqtrade/user_data/config.json
scripts/download_data.sh 20250701-20260907
```

`download_data.sh` states the exchange, pairs, timeframes and timerange
explicitly — no defaults that drift with the calendar — and runs the paper guard
first.

**Freeze protection.** If a dataset lock exists *and* the data directory already
holds files, the script refuses to run and exits 2:

```text
DATASET_FROZEN: research/datasets/dataset_v1.lock.json exists and
freqtrade/user_data/data/binance already holds data.
```

Re-downloading mid-protocol would move fingerprints underneath an experiment
that has already been recorded. Overriding requires `ALLOW_REFREEZE=1` and a
written reason.

## 3. Deep audit after download (mandatory)

```bash
python3 scripts/audit_data.py \
  --data-dir freqtrade/user_data/data/binance \
  --pair BTC/USDT --pair ETH/USDT \
  --timeframe 5m --timeframe 1h \
  --out freqtrade/user_data/baseline_v1_data_audit.json \
  --lock research/datasets/dataset_v1.lock.json
```

Per file: SHA-256, row count vs. expected count from the range, duplicate
timestamps, gaps (with examples), off-grid timestamps, NaN/non-finite cells,
invalid OHLC (`high < low`, `high < max(open, close)`, `low > min(open, close)`),
non-positive prices, negative volume, monotonic time.

Across files: BTC/ETH range alignment per timeframe, and an exact
5m → 1h OHLCV reconciliation (open = first, high = max, low = min, close = last,
volume = sum) over every complete hour.

Against the lock: any fingerprint drift, any file present but unlocked, any
locked file missing — each is a failure.

Exit 0 prints `DATA_INTEGRITY_GATE = PASS`. Anything else is a failure; exit 3
means no data was found. Every defect class above has a unit test in
`tests/test_data_audit.py` built from synthetic candles, so the auditor itself is
proven to catch what it claims to catch.

## 4. Protocol windows and the regime rationale

Chosen from calendar structure and the *passive* market only — never by looking
at an active strategy's outcome.

| Window | Range | Role |
| --- | --- | --- |
| Warm-up | 2025-07-01 → 2025-08-31 | Indicator warm-up only. Never scored. Two months is far more than the ~200 hourly candles an EMA200 needs, so no development bar is computed from a partially warmed indicator. |
| Development | 2025-09-01 → 2026-04-30 (`20250901-20260501`) | 8 months. Open for iteration. |
| Validation | 2026-05-01 → 2026-06-30 (`20260501-20260701`) | 2 months. Opens only after development gates pass and the logic is frozen. |
| Locked OOS | 2026-07-01 → 2026-09-06 (`20260701-20260907`) | **LOCKED.** |

**Regime coverage, stated before any candidate exists.** The development window
is strongly bearish on the passive series: BTC −29.6 %, ETH −48.8 %, a fully
invested 50/50 wallet −39.2 %. A long-only strategy can therefore post a
respectable-looking number purely by holding cash. The exposure-matched passive
line (10 USDT BTC + 10 USDT ETH + 80 USDT cash) returned **−7.83 %**, and that —
not buy-and-hold — is the bar. Any development result must be reported together
with time and capital exposure and with return per unit of exposure.

The corollary is a known weakness, recorded now rather than discovered later:
**Dataset V1 contains no sustained bull regime.** A strategy tuned on it is
tuned on a downtrend. That is a reason to keep the baseline interpretable and to
plan a Dataset V2 covering a different regime — not a reason to widen this
dataset now, which would invalidate the frozen fingerprints.

**Choosing Dataset V2 (when the time comes).** Pick the dates from calendar and
passive-market structure only: name the target regimes (sustained uptrend, a
high-volatility shock, a low-volatility range), verify each is present in the
passive series, and write the rationale down *before* running any active
strategy over it. Selecting V2 dates by looking at how a candidate performs on
them is curve-fitting with extra steps.

## 5. Locked OOS discipline

The OOS window stays closed until the dataset and protocol are frozen, the
baseline logic is frozen, and development and validation gates have passed.
Three mechanisms enforce it, and all three must be defeated deliberately:

* `freqtrade/user_data/baseline_benchmarks.py --period oos` exits 3 with
  `OOS_LOCKED` unless `--unlock-oos` is passed;
* `research/record_experiment.py summarize` refuses a record labelled `oos`
  without `--unlock-oos`;
* the dataset lock marks the window `LOCKED`.

If OOS is inspected and then used to change the system: **`OOS = BURNED`**, and a
new future holdout or forward paper period is required. If the sample is too
small to decide: **`OOS = INCONCLUSIVE`** — do not tune to it.
